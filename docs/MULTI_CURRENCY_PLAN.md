# خطة تعدد العملات

## القرارات (متفق عليها)
- العملة الأساسية للحسابات: **جنيه مصري (EGP)**.
- سعر الصرف: **يتجاب تلقائياً من الإنترنت يومياً**، ويقدر المستخدم **يعدّله يدوياً**.
- كل فاتورة/دفعة بتتسجل بعملتها + سعر الصرف وقت الحفظ، والقيد المحاسبي دايماً بالجنيه.

## 1. قاعدة البيانات (SQL)
جداول جديدة:
- `currencies(code pk, name_ar, name_en, symbol, is_base bool)` — EGP (أساسية)، USD، EUR، SAR، AED كبداية.
- `exchange_rates(id, currency_code, rate_date, rate numeric(18,6) check(rate>0), source text check(source in ('auto','manual')), unique(currency_code, rate_date))` — الرate = كام جنيه لكل وحدة من العملة.

تعديلات على الجداول الموجودة:
- `sales_invoices`, `purchase_invoices`, `payments`: إضافة `currency_code text default 'EGP'`, و`fx_rate numeric(18,6) default 1`, و`total_base numeric(14,2)` (الإجمالي بالجنيه).
- القيود (`journal_lines`) تفضل بالجنيه، لا تغيير في شكلها.

## 2. الدوال اللي لازم تتعدّل (منطق القيد)
الدوال دي بتكتب القيود، وكلها لازم تستخدم `total_base` بدل `total` عند الترحيل:
- `create_sale`, `create_purchase`, `create_sales_return`, `create_purchase_return`
- `create_sale_from_delivery`, `create_purchase_invoice_from_receipt`, `record_pos_sale`
- `edit_sales_invoice`, `cancel_sales_invoice`
- `rebuild_journal` (إعادة بناء القيود)
- `refresh_sales_invoice_paid`, `refresh_purchase_invoice_paid`
- دوال الدفعات (`payments`) وفروق سعر الصرف.

**قاعدة أساسية:** فرق سعر الصرف (الفرق بين سعر الفاتورة وسعر السداد) يتسجل في حساب مستقل "أرباح/خسائر فروق العملة"، عشان الأرباح والخسائر تبقى صح.

## 3. جلب سعر الصرف
- **الطريقة الموصى بيها:** Supabase Edge Function مجدولة يومياً تجيب السعر من مصدر موثوق وتكتبه في `exchange_rates` بـ `source='auto'`.
- لو المصدر وقع، يتستخدم آخر سعر متسجل، والواجهة تعرض تاريخ السعر.
- **الواجهة:** صفحة "أسعار الصرف" تعرض السعر الحالي وتسمح بالتعديل اليدوي (`source='manual'`).
- ملاحظة: الواجهة نفسها ما تتصلش بمصدر خارجي مباشرة، عشان سياسة الأمان (CSP) تسمح بس بـ Supabase.

## 4. الواجهة
- اختيار العملة في فاتورة البيع/الشراء والدفع، والسعر يتملى تلقائياً من آخر سعر وقابل للتعديل.
- الفاتورة تطبع بالعملة الأصلية + المعادل بالجنيه.
- التقارير والأرباح والموازنة كلها تعرض **بالجنيه**.

## 5. الاختبار (قبل أي نشر)
- سيناريوهات معروفة النتيجة: فاتورة بيع بالدولار، سداد بعد تغيير السعر، إلغاء، تعديل، مرتجع.
- التأكد من إن ميزان المراجعة متوازن بعد كل سيناريو (`tests/check_erp.py`).
- التأكد من إن فرق السعر بيظهر في حساب الفروق.

## 6. الترتيب والوقت المتوقع
1. **SQL + الدوال (المرحلة الأصعب):** الجداول، وتعديل دوال القيود، واختبارها على مشروع تجريبي. (أيام كتير، لأنه بيلمس المحاسبة كلها.)
2. **جلب السعر والصفحة:** Edge Function + صفحة أسعار الصرف.
3. **الواجهة:** اختيار العملة في الفواتير والدفعات، والطباعة.
4. **التقارير:** تحويلها للجنيه، واختبارها.

## ملاحظة صريحة
المرحلة 1 بتغيّر منطق المحاسبة نفسه، ولازم تتختبر على مشروع Supabase حقيقي (أو تجريبي) قبل ما تتنشر. ده مش شغل ينفع يتعمل من غير تشغيل فعلي.
